# New Tibet identity

A focused Green Book / Blue Book signup app with four book photos, a random-code challenge, a short video message, private ZKPassport age/duplicate-passport checks, a required display name (pseudonyms welcome) and optional contact details, optional email/WhatsApp verification, optional passkey enrollment, and a manual-review submission screen. Submitted applications open five tabs: Announcements, Petitions, Chat, Wallet, and Profile. Announcements is the default after submission, acceptance, sign-in, and receipt restoration; Profile is last. On mobile they sit at the bottom; at 900px and wider they become a left sidebar. Desktop application steps also use a sidebar. The header is 52px high. The mobile-first interface uses the website’s Inter and IBM Plex Mono fonts, high-contrast text, white backgrounds, and large touch targets. Lapis navy actions and the supplied orange-knot logos retain the newtibet.com branding. The supplied blue and white New Tibet SVG logos live in `public/assets/`, with their unused export padding trimmed; the knot symbol also serves as the favicon. Fonts are self-hosted with their licenses in `public/assets/fonts/`.

The public demo keeps documents and contacts in page memory, and saves only application receipts/status events and inbox read state on this browser. Reloading reopens Announcements without retaining names, contacts, media, proofs, or wallet material. Restart demo clears the saved receipt. It simulates verification codes and review messages with explicit labels. The separate backend implements private Google Drive uploads, Google Sheets records, AppSheet review callbacks, Resend email codes, Meta WhatsApp templates, server-verified WebAuthn registration, and a persistent notification outbox.

Each demo step has a footer shortcut. Upload sample photos adds realistic fictional booklets for Tenzin Dolma. The revised covers and pages use public Green/Blue Book references while retaining visible sample markings. Upload sample video adds an 18-second narrated photo montage for the selected book, with audio and captions. A complete sample set uses example code 534216 to match the clip; adding missing samples preserves existing uploads and their challenge. The generated portrait and original prompts are documented in [demo asset notes](docs/DEMO-ASSETS.md); revised book prompts, references, and video production are in [updated media notes](docs/DEMO-MEDIA-V2.md). Skip advances ordinary steps, omits unverified optional contacts, bypasses demo verification and wallet setup, and previews acceptance in Announcements after review. The member app has Restart demo. Skipped passport checks remain labeled as skipped; omitted contacts are shown as not provided, with in-app updates available. These shortcuts are hidden and inactive in live mode.

The wallet step illustrates biometric/passkey protection for an Ethereum wallet and New Tibet Coin ($TIBET). In the demo, a compatible passkey's client-side PRF encrypts an Ethereum wallet backup; the alternative generates twelve BIP-39 recovery words and checks three words before clearing them from the page. Wallet material remains in page memory and disappears on reload. This is not a funded wallet product: the $TIBET contract is unspecified, transfers and token issuance are unavailable, and persistent encrypted backup/recovery are not implemented. Live mode registers an account passkey only.

Everyone can browse petitions, read their full text and view supporter totals, including Blue Book members and pending or declined applicants. Creating and supporting petitions remains restricted to accepted Green Book holders. Eligible demo profiles can create a local petition and support each petition once. Five sample petitions cover English access to CTA documents and sessions, Tibetan Charter reform, future planning, overseas community resources and youth participation. Their full text preserves the supplied questions. Sample petitions include supporter totals and progress toward goals; created petitions start at zero. These are illustrative results, not live votes or published petitions.

Chat has a WhatsApp-style conversation list, search, private/group message views, and separate drafts. It describes the planned native app as a direct BitChat fork, explaining Bluetooth relays, censorship resistance, and messages waiting for a route. Messages in this website are local demo text, not encrypted or delivered over a mesh. Live petitions remain empty and live chat requires the native app.

The Wallet tab begins with a sample balance of 1,250.00 $TIBET. A local integer-based ledger lets users review and confirm a demo swap to USD, then preview a withdrawal to a masked sample bank account. Balances and activity update after confirmation. The fixed $0.12 example rate is not a market price. No real bank details are collected, money is moved, exchange is contacted, or Ethereum transaction is signed. Reloading clears local petitions, chats, and demo wallet activity; the inbox receipt and read state survive. Live mode disables these features until their services are implemented.


A display name is required; it can be a pseudonym and does not need to be a real name. Email and phone number can be left blank. Any contact that is provided must be verified; the book photos, video, review consent, and live passport proof remain required. Those uploads can contain personally identifiable information. This app does not claim anonymous book verification.

Announcements is a one-way channel: application receipts and review decisions are private to the applicant, while authorized New Tibet announcements are shared with members. A compact channel bar and full-height chronological message feed replace the large heading and receipt block. It supports unread badges, filters, visible message bodies, mark-as-read, refresh and a link to the application record. The live backend stores events and read receipts in SQLite, updates while the app is open, and supports returning with a discoverable passkey without contact details. Members cannot post or reply. No operating-system/background push is implemented. See [inbox integration](docs/INBOX.md) for publisher authorization and endpoints. The GitHub Pages site remains in demo mode; live publishing needs the configured backend.

Chat fills the screen beside the desktop sidebar, with no outer card margins or page header. The conversation list and message pane scroll independently, and the composer stays at the bottom. On mobile it fills the area above the app navigation and demo footer. Bluetooth information is in an info dialog instead of taking space above the chat.

```sh
npm ci
npm run dev
npm test
npm run build
```

Open `http://localhost:4173`. The tracked passport and wallet SDK bundles support the static app in `public/`; `npm run build` regenerates them from the pinned dependencies. The GitHub Actions workflow publishes `dist/` to Pages. See [integration setup](docs/SETUP.md) for provider accounts, templates, AppSheet configuration, backend hosting, and switching to live mode. No secrets belong in the frontend or repository. The preview can generate a ZKPassport request but cannot verify it or enforce global uniqueness without the configured backend. Passport requests disclose no nationality, name, birth date, or passport number; New Tibet receives proofs and a scoped duplicate-registration identifier.

In demo mode, `?preview=announcements` opens the default inbox, `?preview=review` opens a pending inbox, and `?preview=profile` opens the accepted identity profile. Simulated decisions move to the top of a distinct result screen. The selected decision is disabled, WhatsApp previews remain clearly labeled, and accepted profiles retain the actual passport/contact verification state. These entry points and review controls are disabled in live mode; only the backend's accepted status opens a live identity card. Pending and declined applications retain their inbox and application record. Profiles use the applicant's name, book type, application reference, and initials. Tenzin's fictional demo profile uses her generated portrait; live profiles use initials. A missing name uses a member reference instead. No birth date, citizenship, or verification data is invented. Demo profiles are labeled as previews.

Setup order: Document and display name → Book photos → Video → Passport → Wallet security → optional Contact details. Book/video review consent is collected at the first step. Contacts are the final, lowest priority step; in-app updates work without them. Demo Skip fills a fictional display name and review consent where needed; ordinary submission and the live backend always require a nonblank display name. Disabled navigation labels remain fully opaque and dark for readability.
