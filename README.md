# New Tibet identity

A focused Green Book / Blue Book signup app with four book photos, a random-code challenge, a short video message, private ZKPassport age/duplicate-passport checks, a required display name (pseudonyms welcome) and optional contact details, optional email/WhatsApp verification, optional passkey enrollment, and a manual-review submission screen. Members without a book can instead join using an invitation from a verified book holder. An **Explore New Tibet** button opens the app immediately without signup. Profile contains the membership and verification flow, with a five-stage progress ladder showing 100 free $TIBET for book approval and another 100 for optional NFC verification; security and contact setup carry no extra coin reward. Forms open within Profile while all app navigation remains available. Leaving a form preserves its draft in page memory, and reloading retains only an exploration preference or an existing application receipt. Unverified visitors and pending/declined applicants see locked chat, wallet and ecosystem views; member conversations and message composers are absent from the DOM. Member announcements require acceptance, while private application receipts remain accessible during review. Everyone can read petitions; support and creation require accepted Green Book membership. All visitors and submitted applications have five primary tabs: Profile, Wallet, Chat, Petitions and Ecosystem. Announcements opens from the top-right notification bell, with an unread badge and a close action that returns to the previous screen. Announcements is the default after submission, acceptance, sign-in, and receipt restoration. On mobile they sit at the bottom; at 900px and wider they become a left sidebar. Desktop application steps also use a sidebar. The account header is a compact, sticky 52px bar. The Bluetooth mesh diagram appears only in the explanation dialog. The mobile-first interface uses the website’s Inter and IBM Plex Mono fonts, high-contrast text, white backgrounds, and large touch targets. Lapis navy actions and the supplied orange-knot logos retain the newtibet.com branding. The supplied blue and white New Tibet SVG logos live in `public/assets/`, with their unused export padding trimmed; the knot symbol also serves as the favicon. Fonts are self-hosted with their licenses in `public/assets/fonts/`.

### Vouched membership and invitations

Accepted Green or Blue Book members have an **Invite** button on Profile. Its modal generates a code and a copyable message with a signup link for sharing manually. Signup offers **Vouched by a member**, requiring only the code and chosen display name. This creates accepted vouched membership without book evidence, and never represents it as Green Book verification. Vouched members can read petitions but cannot create/support them or issue further invitations. The 100 $TIBET signup reward remains tied to book verification; optional NFC and example learning rewards remain available.

The live backend exposes authenticated `POST /api/invites` and `POST /api/invites/redeem`. Codes have 72 bits of random entropy, expire in seven days, and are stored only as keyed hashes. Issuance is limited to 20 codes per member per day; redemption is rate-limited by session and IP. Current inviter eligibility is rechecked at redemption, and the account, code consumption, private receipt and session association are committed atomically. Retrying a successful redemption in the same session returns the same account. The private account keeps the inviter reference; summaries, QR checks and wallet passes do not reveal it. Vouched accounts have no document-review spreadsheet row, and later contact/passkey upgrades stay in the account database.

GitHub Pages is a static demo. Its distinct `DEMO-NT-…` codes contain a public typo checksum, work between browsers, and cannot authenticate an inviter or enforce global single use. The UI states that limitation; the live backend rejects demo codes. Browser storage retains only fingerprints to prevent local reuse, and the minimal membership receipt contains no raw invitation code or chosen display name. No email or WhatsApp message is sent automatically.

The welcome screen says Join New Tibet, highlights privacy, passkey security and cryptocurrency, and displays the requested “Upon book verification you receive 100 free $TIBET coins” message. Coin issuance remains unimplemented. Its mobile phone slideshow renders the actual digital ID, Wallet, Chat, Petitions, Ecosystem and Announcements using read-only, fictional showcase frames; changes to the application’s renderers and CSS automatically appear in the slideshow. Controls include arrows, screen dots, pause/play, keyboard navigation and mobile swipe. Reduced motion pauses autoplay. Showcase frames never restore or save the viewer’s inbox, access their session or call the backend. See [welcome preview notes](docs/WELCOME.md).

The public demo keeps documents and contacts in page memory, and saves only application receipts/status events and inbox read state on this browser. Reloading reopens Announcements without retaining names, contacts, media, proofs, or wallet material. Restart demo clears the saved receipt. It simulates verification codes and review messages with explicit labels. The separate backend implements private Google Drive uploads, Google Sheets records, AppSheet review callbacks, Resend email codes, Meta WhatsApp templates, server-verified WebAuthn registration, and a persistent notification outbox.

The wallet step illustrates biometric/passkey protection for an Ethereum wallet and New Tibet Coin ($TIBET). In the demo, a compatible passkey's client-side PRF encrypts an Ethereum wallet backup; the alternative generates twelve BIP-39 recovery words and checks three words before clearing them from the page. Wallet material remains in page memory and disappears on reload. This is not a funded wallet product: the $TIBET contract is unspecified, transfers and token issuance are unavailable, and persistent encrypted backup/recovery are not implemented. Live mode registers an account passkey only.

Chat has a WhatsApp-style conversation list, search, private/group message views, and separate drafts. It describes the planned native app as a direct BitChat fork, explaining Bluetooth relays, censorship resistance, and messages waiting for a route. Messages in this website are local demo text, not encrypted or delivered over a mesh. Live petitions remain empty and live chat requires the native app.

Demo wallets begin empty. Membership acceptance credits a single 100.00 $TIBET signup reward, dated to the application acceptance event, and adds a “1” notification on the Wallet tab. Opening Wallet clears that badge; its read state survives reloads independently of Announcements. The activity timeline shows the incoming verification reward and dated sends, swaps and withdrawals, newest first. Repeated renders or simulated decisions do not add another reward. Send searches three fictional registered usernames (@sonam.tsering, @pema.dolkar and @lobsang.norbu). The user chooses a recipient and amount, then reviews the full recipient credit, an illustrative 0.25 $TIBET gas fee, and the total debit before confirming. Max reserves the fee. The local integer ledger credits that sample recipient, debits the sender including gas, and records the fee separately; replayed or altered quotes are rejected. Users can also review and confirm a demo swap to USD, then preview a withdrawal to a masked sample bank account. Balances and activity update after confirmation. The fixed $0.12 example rate is not a market price. No real bank details are collected, money is moved, exchange is contacted, or Ethereum transaction is signed. Reloading clears local petitions, chats, and demo sends/swaps/withdrawals; the accepted receipt reconstructs the same signup reward with its original date. The inbox receipt and reward/inbox read state survive. No wallet keys, balances or outgoing transaction details are saved. Live mode disables these features until their services are implemented.


A display name is required; it can be a pseudonym and does not need to be a real name. Email and phone number can be left blank. Any contact that is provided must be verified; the book photos, video and review consent remain required. Passport NFC is an optional upgrade. Those uploads can contain personally identifiable information. This app does not claim anonymous book verification.

Announcements is a one-way channel: application receipts and review decisions are private to the applicant, while authorized New Tibet announcements are shared with members. A compact channel bar and full-height chronological message feed replace the large heading and receipt block. The message feed starts directly below the channel bar, with unread badges, visible message bodies, mark-as-read and refresh. Application records remain available in Profile. Opening Announcements automatically marks current messages read and clears the notification bell badge; this survives reload. New updates received on other tabs show a badge until Announcements is opened again. The live backend stores events and read receipts in SQLite, updates while the app is open, and supports returning with a discoverable passkey without contact details. Members cannot post or reply. No operating-system/background push is implemented. See [inbox integration](docs/INBOX.md) for publisher authorization and endpoints. The GitHub Pages site remains in demo mode; live publishing needs the configured backend.

Chat fills the screen beside the desktop sidebar, with no outer card margins or page header. The conversation list and message pane scroll independently, and the composer stays at the bottom. On mobile it fills the area above the app navigation and demo footer. A compact notice stays visible in the conversation list and open chats, explaining that the native app will relay messages through Bluetooth mesh without a centralised intermediary to censor them. The info dialog explains nearby relays, delivery delays and the distinction between the website demo and native Bluetooth messaging.


Open `http://localhost:4173`. The tracked passport and wallet SDK bundles support the static app in `public/`; `npm run build` regenerates them from the pinned dependencies. The GitHub Actions workflow publishes `dist/` to Pages. See [integration setup](docs/SETUP.md) for provider accounts, templates, AppSheet configuration, backend hosting, and switching to live mode. No secrets belong in the frontend or repository. The preview can generate a ZKPassport request but cannot verify it or enforce global uniqueness without the configured backend. Passport requests disclose no nationality, name, birth date, or passport number; New Tibet receives proofs and a scoped duplicate-registration identifier.

In demo mode, `?preview=announcements` opens the default inbox, `?preview=review` opens a pending inbox, and `?preview=profile` opens the accepted identity profile. Simulated decisions move to the top of a distinct result screen. The selected decision is disabled, WhatsApp previews remain clearly labeled, and accepted profiles retain the actual passport/contact verification state. These entry points and review controls are disabled in live mode; only the backend's accepted status opens a live identity card. Pending and declined applications retain their inbox and application record. Profiles use the applicant's name, book type, application reference, and initials. Tenzin's fictional demo profile uses her generated portrait; live profiles use initials. A missing name uses a member reference instead. No birth date, citizenship, or verification data is invented. Demo profiles are labeled as previews.

Registration order: book and display name → verification evidence (photos, video and consent). After submission, members can add optional passport NFC verification, wallet/account security, and then optional contact details. Contacts remain the lowest-priority setup; in-app updates work without them. Demo Skip fills a fictional display name and review consent where needed; ordinary submission and the live backend always require a nonblank display name. Disabled navigation labels remain fully opaque and dark for readability.
