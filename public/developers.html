How sign-in would work

  1. 1Your application

    A member chooses Sign in with New Tibet ID.

    →
  2. 2New Tibet

    They unlock with their passkey and approve the information shared.

    →
  3. 3Your server

    Exchange a one-time code, validate the response, and create a session.

An account identifier and approved membership status are shared. Identity evidence stays with New Tibet; private passkey material stays on the member’s device or password manager.

STEP 3

Handle authentication on your server

The proposed flow uses OpenID Connect Authorization Code with PKCE. The Node.js example below uses openid-client v6 to discover the provider and validate the response.

  1. Start sign-in. Generate a fresh verifier, state and nonce. Save them in a short-lived server-side session before redirecting the member.
  2. Handle the callback. Exchange the code, check state and nonce, and require a validated ID token. Consume the sign-in attempt once, including on failure.
  3. Create your session. Find or create a local user using the issuer and subject together. Rotate the session ID after authentication.

Allow a Green Book feature only after your server validates authentication and confirms both verified: true and book_type: "green". Missing, unverified or Blue Book status must not unlock that feature. General content can remain visible to everyone.

Claims reflect membership at issuance. Require a fresh sign-in for sensitive membership actions and define a short session policy; a saved claim cannot guarantee that membership is still active.

Keep identity evidence out of your application

The intended partner response excludes book photos, passport scans, video, biometrics, private keys and wallet recovery words. Request the minimum permissions and obtain clear member consent. Do not treat a display name as a legal identity.

Prepare for launch

Once partner authentication is enabled, test the complete flow with New Tibet before enabling it for your users.

  • Confirm the issuer, scopes, claim names, token authentication method and exact callback registration.
  • Test cancelled sign-ins, expired codes, wrong state or nonce, replayed callbacks and invalid tokens.
  • Check Green Book, Blue Book and missing membership status; enforce restricted actions on the server.
  • Confirm that consent, session expiry, sign-out and membership changes behave as users expect.
  • Test keyboard access and the complete redirect flow on iPhone and Android.
